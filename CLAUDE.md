## Project

A small internal web app that replaces an Excel-based stocktaking (재고조사) workflow. It manages four kinds of data: 공통코드 (common codes), 품목 (items), 조사기록 (stocktake records), and 센서 바코드 (individually-tracked sensor barcodes), across five pages (공통코드 등록 / 품목등록 / 재고등록 / 센서 재고 등록 / 현황). No login/auth — this is a single-user internal tool; audit fields (`created_by`/`updated_by`) are always the fixed string `"admin"`.

`example/ORG_updated_fixed.xlsx` (local only — `example/` is gitignored and not in the repo) is the original Excel-based inventory data this app replaces (4 sheets: `0_공통설정`, `1_품목등록`, `2_입출고입력`, `3_현재고현황`). Its text is valid UTF-8 — apparent mojibake when inspecting it from a shell is just this Windows terminal's console codepage misrendering UTF-8 output; don't re-diagnose it as file corruption. It has already been imported once (see [guide/HISTORY.md](guide/HISTORY.md)) via a one-off script (not kept in the repo) using `openpyxl`-incompatible raw XML parsing, since `openpyxl` fails on this file's `styles.xml`. One real data quality issue found during that import: many `1_품목등록`/`3_현재고현황` rows have a plain numeric value (not a location name) in the 위치 column — cross-checked against `2_입출고입력`'s 날짜 column, these are almost certainly leftover date-serial values from a copy/paste error in the original sheet, not real locations, so they were imported with `location_id = NULL` rather than fabricated.

## Commands

```
docker compose up -d                        # start local MariaDB (first time: cp .env.example .env, then change the DB_PASSWORD / DB_ROOT_PASSWORD placeholders — no password defaults exist in code or compose, so it fails without them)
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt   # (Windows; use .venv/bin on macOS/Linux)
.venv/Scripts/python scripts/generate_dev_cert.py   # first time, and again whenever the LAN IP changes
.venv/Scripts/python -m uvicorn app.main:app --reload --port 8010 --ssl-keyfile certs/dev-key.pem --ssl-certfile certs/dev-cert.pem
docker compose down -v                      # stop MariaDB and wipe its data volume
```

Port 8000 is already in use on this machine by another project (seeErp, forwarded via Docker Desktop/WSL), so this app defaults to **8010** instead. Nothing in the code hardcodes a port — pass `--port <n>` to uvicorn to use a different one.

**The app is served over HTTPS, not HTTP, using a self-signed cert** (`certs/dev-{key,cert}.pem`, generated by `scripts/generate_dev_cert.py`, gitignored) — e.g. `https://192.168.0.3:8010`, not `http://...`. This exists because `getUserMedia` (camera access, for the 센서 재고 등록 scan page) only works in a secure context, and a LAN IP over plain HTTP doesn't qualify; serving HTTPS instead was the user's explicit choice after being told about this limitation. Consequences worth knowing:
- Passing `--ssl-keyfile`/`--ssl-certfile` makes uvicorn speak **TLS-only** on that port — plain `http://` requests to it no longer get a response at all.
- The cert's SAN list is baked in at generation time from whatever the machine's LAN IP was then. **This PC's IP changes (DHCP) — when it does, re-run `generate_dev_cert.py` and restart uvicorn**, or the cert won't match the new address.
- It's self-signed, so every browser (including the phone accessing it) shows a "not private"/"not secure" interstitial on first visit — that's expected; the user has to click through (Chrome: Advanced → Proceed), there's no way to avoid it without a real CA-issued cert.
- When testing with `curl`/`requests`/Playwright against this instance, you need `-k` / `verify=False` / `ignore_https_errors=True` respectively, or the self-signed cert will fail verification.

There is no configured lint/test/build tooling yet — none exists in this repo, so don't assume `pytest`/`ruff`/etc. are wired up.

On startup, `app/main.py` calls `Base.metadata.create_all` (no migrations/Alembic — tables are created directly from the SQLAlchemy models) and seeds the four fixed common-code groups (`UNIT`/`LOCATION`/`CATEGORY`/`SIZE_ABBR`). The actual code values inside each group are empty until entered via the 공통코드 등록 page — items can't be created until at least one 구분 and one 단위 code exist.

**Every `/static/css/*.css` and `/static/js/*.js` reference in the templates is suffixed `?v={{ asset_version }}`** (`app/core/templates.py` sets this Jinja global to the server's start timestamp). This exists because a real device (a phone that had visited before) kept rendering a stale cached `style.css` after an edit — the HTML was current but the CSS wasn't, so new layout rules silently didn't apply. **Restarting the server is what busts the cache** for every client, including ones that never reload otherwise; editing a static file without restarting won't be picked up by a browser that already cached it under the old `?v=`.

**`create_all` only creates missing tables — it never alters an existing one.** This DB already holds real imported data (see below), so adding a column to an existing model (e.g. the `item_no`/`barcode`/`barcode_prefix` additions in [guide/HISTORY.md](guide/HISTORY.md)) requires a manual `ALTER TABLE` against the running MariaDB before restarting the app, not just an edit to the model file.

## Architecture

```
Browser → Jinja2 Templates → Vanilla JS (fetch) → FastAPI Router → MariaDB
```

```
app/
├── api/            # common_codes.py, items.py, stocktakes.py (also serves GET /api/stocktakes/status), sensor_barcodes.py (POST /api/sensor-barcodes/scan), pages.py (renders the 5 HTML pages)
├── core/           # config.py (pydantic-settings, reads .env), database.py (engine/session/Base), templates.py (shared Jinja2Templates instance)
├── models/         # mixins.py (AuditMixin: created_by/created_at/updated_by/updated_at/is_active), common_code.py, item.py, stocktake.py, sensor_barcode.py
├── schemas/        # Pydantic request/response models, one file per domain
├── crud/           # DB query functions — one module per domain, filters are optional kwargs (not forked functions)
├── static/{css,js}/
├── templates/
│   ├── components/  # nav.html, toast.html
│   ├── pages/        # common_codes.html, items.html, stocktakes.html, scan.html, status.html
│   └── layout.html
└── main.py
```

Key design points worth knowing before touching this code:

- **Common codes are structural, not hardcoded values.** The 4 group codes (`CommonCodeGroupEnum` in `app/models/common_code.py`: `UNIT`, `LOCATION`, `CATEGORY`, `SIZE_ABBR`) are fixed in code because the set of groups is part of the requirements, but every actual code *value* inside a group lives only in the `common_codes` table, managed via the 공통코드 등록 page. Never hardcode a status/category string elsewhere.
- **There is no API to move a `common_codes` row between groups** — `CommonCodeUpdate` deliberately only covers `code`/`name`/`sort_order`/`is_active`, not `group_id` (moving groups isn't a normal use-case for the 공통코드 page's own UI, which only ever creates a code already scoped to the currently-selected group tab). It has already happened once that the user picked the wrong group tab and bulk-added a batch of codes under it (40 위치-shaped codes like "1-4".."8-3" ended up under UNIT) — fixing that required a one-off script directly against the SQLAlchemy session (check for `(group_id, code)` UNIQUE collisions with the destination group first, and that no item actually references the misplaced rows via `unit_id`/`category_id` before moving them). If this recurs, that's the pattern — not a feature to build into the API for a one-time cleanup.
- **Items reference common codes by FK id** (`category_id`, `unit_id`, `location_id`, `size_abbr_id`), not by code string — the frontend selects populate `<option value="{id}">` from `GET /api/common-codes?group_code=...`.
- **`item_no`/`barcode`/`barcode_prefix` are plain optional string columns on `items`**, not routed through common codes — they're per-item identifiers, not a shared classification, so they don't belong in `common_codes`. Unlike category/unit/location/size, the item-name autocomplete deliberately does not copy them onto a new item draft (copying one across items would fabricate a duplicate identifier).
- **`barcode` and `barcode_prefix` (바코드구분) are two unrelated fields — do not conflate them.** `barcode` is a general free-text identifier, only ever used for fuzzy search. `barcode_prefix` is specifically for 센서 등 개체마다 고유한 전체 바코드를 갖는 품목: it is NOT the full barcode value, only the leading substring shared by every physical unit of that product line (e.g. `barcode_prefix="si"` while actual scanned units are `"si-0001"`, `"si-0002"`, ...). It has a DB `UNIQUE` constraint (one product line owns a given prefix), checked proactively via `crud/item.py::barcode_prefix_exists` before insert/update (so a duplicate is a clean 409, not a raw `IntegrityError` 500 — a real bug caught and fixed during development).
- **Text search is shared across item/stocktake/status queries** via `crud/item.py::search_clause(search)`, which OR-matches `item_name`/`item_no`/`barcode`/`barcode_prefix`. `crud/stocktake.py` imports and reuses it instead of re-implementing the condition.
- **센서 재고 등록 (`/scan`) does not touch `stocktake_records` at all.** It scans into a separate table, `sensor_barcodes` (`item_id`, `barcode` UNIQUE) — one row per physical unit's own unique barcode, so sensor "count" is derived by counting active rows, not by an incrementing quantity field. The page has two modes, toggled by the user, because **decreasing sensor stock through the general 재고 등록 page can't say *which* unit left — only scanning that unit's own barcode can:**
  - 입고 (`POST /api/sensor-barcodes/scan {barcode}`): if the value is already an *active* row, 409 (re-scanning the same unit isn't a second count). If it's a previously-removed (inactive) row, reactivate it rather than inserting (`barcode` is globally `UNIQUE`, so a unit leaving and later coming back must reuse its row — `crud/sensor_barcode.py::reactivate_barcode`). Otherwise resolve which item it belongs to via `crud/item.py::find_item_by_scanned_barcode`, a **prefix** match (`scanned_value.startswith(item.barcode_prefix)`, longest prefix wins on overlap) — not an exact match, since the scanned value is always longer than the stored `barcode_prefix`. No match is a 404; it never fabricates a new item or guesses.
  - 출고 (`POST /api/sensor-barcodes/remove {barcode}`): exact match on an *active* row, soft-deletes it. No match (never registered, or already removed) is a 404.
  - The 현황 page's expanded barcode list also exposes a per-barcode 제거 button (`DELETE /api/sensor-barcodes/{id}`, by id) for correcting the list without rescanning.
  - Units whose barcode is lost/missing are registered/adjusted via the ordinary 재고 등록 page instead of scanning — see the `current_stock` reconciliation below for how that manual number and the barcode count combine rather than living as two disconnected totals.
  - The page (`static/js/scan.js`) keeps one input permanently focused for continuous scanner input and shows a running client-side log of the session's scans, including which mode each entry was.
  - **A phone camera is a second input path into the same flow, not a separate one.** `scan.js` extracts `processScan(barcode)` so the physical-scanner path (Enter → form submit) and the camera's decode callback both call the identical function — don't reimplement the add/remove branching a second time if touching the camera code. Camera decoding is `html5-qrcode@2.3.8` loaded via CDN in `scan.html` (the project has no build step, so this is a plain `<script>` tag like the Pretendard font, not an npm dependency); `startCamera()`/`stopCamera()` toggle a `Html5Qrcode` instance targeting `#camera-reader`. **`getUserMedia` (camera access) only works in a secure context (HTTPS or `localhost`)**, which is why this app is now served over HTTPS (see the Commands section above) instead of plain HTTP — `cameraSupported()` still detects an insecure context and shows a Korean message explaining it, as a defensive fallback in case someone reverts to plain HTTP.
  - **The camera decodes continuously in the background, but only one specific decode gets acted on — the one right after the user presses "스캔하기".** `Html5Qrcode.start()`'s callback (`onCameraDecoded`) fires nonstop at the configured fps the whole time the camera is open; there's no way to make the underlying library itself scan only once on demand. So decode results are gated by a module-level `armed` flag instead: `requestCapture()` (the capture button's handler) sets `armed = true`; `onCameraDecoded` does nothing unless `armed`, and immediately sets it back to `false` before calling `processScan` so exactly one barcode gets processed per button press, however many frames get decoded in between. This replaced an earlier version that auto-processed every decode continuously (debounced 1.5s by repeated value) — the user found that too fast/uncontrolled ("스캔 간격이 좁음") and asked for an explicit press-to-scan model instead, which is also simpler code (no time-based dedupe to reason about).
- **All deletes are soft** (`is_active` flips to false via a `deactivate_*` crud function). There is no physical `DELETE FROM` anywhere; list endpoints default to `is_active=True`.
- **`current_stock` is the one number that answers "how many do we actually have" — don't read `last_quantity` or `barcode_count` alone as *the* stock level.** `crud/stocktake.py::get_status` computes `current_stock = barcode_count + (last_quantity or 0)` (None only when both are absent — never counted, no barcodes). This exists because treating 재고 등록's manual snapshot and `sensor_barcodes`' scan count as two unrelated numbers was flagged directly by the user as the actual problem: for a barcode-tracked item, `last_quantity` no longer means "total stock", it means **only the barcode-less portion** (units a user is manually accounting for, e.g. ones whose barcode is lost) — the 재고 등록 form detects this (`barcode_prefix` set, or `barcode_count > 0`) and relabels its quantity field from "수량" to "바코드 없는 보유 수량" accordingly (`static/js/stocktakes.js::isSensorTracked`/`updateSelectedItemUi`). For ordinary items `barcode_count` is always 0, so `current_stock` just equals `last_quantity` as before — no behavior change there.
  - **Typing into that relabeled field does NOT set total stock — it's easy to get this backwards.** E.g. barcode 3 + manual 1 = current_stock 4; typing "2" into the field doesn't make total 2, it makes manual 2 so total becomes **5**. Because this is a real, easy user mistake (confirmed directly), the form shows a `#stock-breakdown` card (바코드 수량 / 바코드 없는 수량 / 총 현재고, the last one bold) whenever the selected item is barcode-tracked, instead of relying on a one-line sentence — `updateSelectedItemUi` toggles `breakdown.hidden` and fills the three spans; it's absent entirely for ordinary items, which keep the original single-line "선택된 품목 / 현재고 N" text.
- **Items can share `item_name` and differ only by 규격 (size) — real imported data has this (복스 대/중/소, 드릴팁 소/대, 케이블타이 소/중, ...).** Anywhere a user picks an item by name (재고 등록's combobox, 품목 등록's similar-item autocomplete), the size has to be visible or they can't tell which same-named item they're selecting — this was a direct, confirmed user complaint. `static/js/common.js::itemSizeLabel(item)` (and the lower-level `sizeDetailText(item)` it wraps) is the one shared formatter for "규격약식(규격상세)" e.g. `소(5 x 20 x 3)`, used in combobox/autocomplete `renderMeta`, the "선택된 품목" label (`품목명 [규격]`), and the 재고 등록 history table's 규격 column. `sizeDetailText` used to be duplicated in `items.js` alone — it's shared now, so add any future size-formatting logic to `common.js`, not page-local files.
- **The 현황 (status) view has no dedicated table.** `crud/stocktake.py::get_status` left-joins two things onto all active items: the latest `stocktake_records` row per item via a `ROW_NUMBER() OVER (PARTITION BY item_id ORDER BY survey_date DESC, id DESC)` window query (items never counted show a null quantity/date), and a `COUNT(sensor_barcodes.id)` grouped by `item_id` for `barcode_count`. **The frontend gates the "N건 보기" button on `barcode_count` itself, not on `item.barcode_prefix` being set** (`static/js/status.js::renderStatusRow`) — a count can outlive a later-cleared prefix, so checking the prefix instead was a real bug caught during testing. The page only fetches the actual list of barcode strings on demand (`GET /api/sensor-barcodes?item_id=...`, triggered by clicking the count) rather than eagerly loading every item's full list.
- **Autocomplete/search reuse the same list endpoints** (e.g. `GET /api/items?search=...&limit=8`) rather than dedicated autocomplete routes — per the "don't fork query functions" rule, filtering is just optional query params.
- **Frontend has no framework.** `static/js/common.js` holds shared fetch/toast/debounce/common-code-cache helpers; `static/js/autocomplete.js` is a generic reusable autocomplete widget (attach to any input+list pair with a `fetchItems` callback) used by the item-registration page, the stocktake-registration page, and (as a combobox, see below) the 재고 등록 item picker.
- **On the 재고 등록 ("재고조사 기록 추가") form, 구분/위치 are not independent input data — they always reflect 품목 등록's own data, never something typed separately for a stocktake record.** Before an item is picked they narrow the item combobox (`category_id`/`location_id` passed to `GET /api/items`); the instant an item is picked, `static/js/stocktakes.js::selectItem` force-syncs both `<select>`s to that item's real `category`/`location` (overwriting whatever was there). Changing either `<select>` afterwards is treated as "start a new search" (`clearSelectedItem`), not as editing the picked item's classification. The item picker itself is a combobox, not a plain autocomplete: `attachAutocomplete(..., { showOnFocus: true })` fetches and shows a (possibly filtered) list as soon as the input is focused, before any typing — this flag is opt-in on the shared widget, so `items.js`'s own autocomplete (which still only searches on input) is unaffected. Selecting an item also prefills the quantity field with its current stock via `GET /api/stocktakes/latest/{item_id}` (plain `step="1"` number input — an earlier version added dedicated +/- buttons, removed per feedback as unnecessary). For barcode-tracked items, typing into that field does not set the total (a real, confirmed user mistake — see the `current_stock` bullet above), so the form shows `#stock-breakdown` — three explicit rows (바코드 수량 / 바코드 없는 수량 / 총 현재고) — instead of a single sentence; it's `hidden` entirely for ordinary items.
- Fixed CSS palette, spacing grid, and font choices are defined once in `static/css/style.css` per the guidelines — extend the `:root` variables there rather than adding one-off colors in templates.
- **Mobile layout lives in one `@media (max-width: 768px)` block at the end of `style.css`**, not scattered per-component rules. It turns the fixed-width left sidebar nav into a horizontally-scrollable top tab bar (`.app-sidebar`/`.nav-list` become flex rows), bumps form/search input font-size to 16px (below that, iOS Safari auto-zooms on focus, which looks like "the UI is broken" — this was the actual user complaint), and widens toasts to fill the screen. Every `<table class="data-table">` across all 5 page templates is wrapped in a `.table-scroll` div (`overflow-x: auto`) so a wide table (e.g. 품목 목록's 11 columns) scrolls within itself instead of blowing out the whole page's width — if you add a new table, wrap it the same way or it won't fit on a phone.
- **품목 목록's leftmost "번호" column is the raw `items.id` (PK), not a recomputed row number** — the user explicitly asked for exactly that ("그냥 db의 idx 출력해도 될듯"), so don't "fix" it into a 1-based sequence later; that would be a deliberate regression. The "전체 N개 · 조회결과 M개" badge next to the "품목 목록" panel title comes from `GET /api/items/count` (`crud/item.py::count_items`), called twice in parallel by `loadItems()` — once with no filters for the total, once with the current search/category/location filters for the match count. `count_items` shares its WHERE-clause building with `get_items` via `_item_filter_conditions` specifically so the two can't silently drift apart (e.g. one gaining a filter the other doesn't honor). **`/count` is registered before `/{item_id}` in `app/api/items.py`** — if you add another item sub-route by literal path, it has to go before the `{item_id}` catch-all too, or FastAPI will try to parse the literal segment as an id.
